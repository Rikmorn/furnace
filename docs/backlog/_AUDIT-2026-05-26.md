## §1. Triggered & ready (highest priority)

The documented trigger condition has fired. Cost-benefit is favourable. Listed in rough "would I do this first" order, but the order is opinion, not constraint.

### 1.1 `typed-uniform-setters.md` — design pass needed before implementation

**Trigger:** "Third or fourth call site doing repetitive `writeBuffer(buf, 0, new Float32Array([...]))` for shader params."

**Current state: 7 call sites.** hello-world has 3 (halo, emissive, plus one more), post has 2 (bloom, vignette), shader has 2 (striped, plasma). Every cookbook addition is going to make this pile worse.

**Why design-first.** The backlog entry lists three implementation choices that affect the API surface materially:
1. Engine vendors a WGSL parser → introspects struct layout (offset, padding, alignment) → consumer just passes `{ threshold: 0.7 }`. Heavy lift but cleanest consumer API.
2. Consumer-declared layout descriptor → `uniformLayout: { threshold: { offset: 0, type: "f32" }, ... }`. Light engine lift but consumer carries the layout knowledge twice (once in WGSL, once in TS).
3. Shader reflection → not available; WebGPU doesn't expose it.

The choice between 1 and 2 has consequences across material AND post (both call sites would adopt the same shape). Picking the wrong one now means a second migration later. **Run a brainstorm session to settle the API before any implementation.**

**Adjacency:** lands cleanly bundled with `material-uniform-setters.md` (per-built-in setters for unlit color, etc.). Same session can settle the consumer-facing API for both built-in materials AND custom-shader params.

### 1.2 `engine-cascade-teardown.md` — diagnostic noise affects all demos today

**Trigger:** none stated, but the entry now documents an observable bug.

**Current state:** *Every* `gpu.dispose(ctx)` after a successful render emits `[furnace/gpu] context disposed with N resource(s) still registered — leak suspected` because `frame.render` lazily allocates the depth texture and per-camera uniform buffers without disposal hooks. Minimum 2 leaked entries per dispose. Affects every cookbook demo's page unload AND every GPU test that creates a ctx.

**Two-stage fix proposed in the entry.** Quick targeted fix (`frame.disposeInternals(ctx)` called from `gpu.dispose`) is ~30 minutes and clears the noise. Proper cascade (`gpu.onDispose(ctx, cb)` hook + self-registering modules) is the right longer-term shape and avoids `gpu.dispose` knowing about `frame.render` internals.

**Recommendation:** ship the targeted fix immediately; design the cascade separately when more modules grow ctx-bound state (post will hit this if it doesn't already — needs verification during implementation).

### 1.3 `material-shader-source-shape.md` — duplicate `createShaderModule` across all materials

**Trigger:** "Next material variant that wants a different vertex shader from the previous one, OR fourth built-in material."

**Current state:** trigger not literally met (still one vertex shader shape across all built-ins), but the smell is **observable at 5 `material.create` call sites** now (camera/render-target/blend/geometry/shader/post — all pass `vertex: source, fragment: source` with the same string). Every material in the codebase allocates two `GPUShaderModule`s for identical source. The two-field API doesn't pay for itself.

**Three options in the entry** (collapse to single source; engine-side dedup; first-class `Shader` resource). Bundle into the same material-API session as `material-uniform-setters.md` since both touch `MaterialDescriptor`.

## §8. Process notes

- **Audit cadence.** Manual audits every ~50 entries OR before major work phases. The accretion from cookbook (5 demo sessions in 3 days = +8 entries, several promotions) shows how fast the backlog grows when a sustained work surface is active. A quick audit after each multi-session work surge keeps the list useful.
- **Pruning discipline.** Several entries flagged §5 are likely defunct because the work that obviated them happened without a backlog-prune step. Adding "scan relevant subdir; delete obsoleted entries" to the post-execution checklist would prevent this drift.
- **Trigger phrasing.** Triggers like "third or fourth call site" measure something the consumer count surfaces naturally. Triggers like "when a real consumer needs X" require an explicit decision to count. Where possible, future entries should prefer the former — measurable, audit-friendly.
