## §1. Triggered & ready (highest priority)

The documented trigger condition has fired. Cost-benefit is favourable. Listed in rough "would I do this first" order, but the order is opinion, not constraint.

### 1.1 `typed-uniform-setters.md` — design pass needed before implementation

**Trigger:** "Third or fourth call site doing repetitive `writeBuffer(buf, 0, new Float32Array([...]))` for shader params."

**Current state: 7 call sites.** hello-world has 3 (halo, emissive, plus one more), post has 2 (bloom, vignette), shader has 2 (striped, plasma). Every cookbook addition is going to make this pile worse.

**Why design-first.** The backlog entry lists three implementation choices that affect the API surface materially:
1. Engine vendors a WGSL parser → introspects struct layout (offset, padding, alignment) → consumer just passes `{ threshold: 0.7 }`. Heavy lift but cleanest consumer API.
2. Consumer-declared layout descriptor → `uniformLayout: { threshold: { offset: 0, type: "f32" }, ... }`. Light engine lift but consumer carries the layout knowledge twice (once in WGSL, once in TS).
3. Shader reflection → not available; WebGPU doesn't expose it.

The choice between 1 and 2 has consequences across material AND post (both call sites would adopt the same shape). Picking the wrong one now means a second migration later. **Run a brainstorm session to settle the API before any implementation.**

**Adjacency:** lands cleanly bundled with `material-uniform-setters.md` (per-built-in setters for unlit color, etc.). Same session can settle the consumer-facing API for both built-in materials AND custom-shader params.

### §9.1 Verb consistency — mostly clean, one outlier

`create` / `destroy` is the universal pair across `material`, `mesh`, `post`, `mesh.createGeometry`/`destroyGeometry`. ✓

**Outlier:** `gpu.dispose(ctx)` uses `dispose` instead of `destroy`. Intentional (context is the root, not a resource), but it creates a small vocabulary tax — newcomers hit `material.destroy` + `mesh.destroy` + `gpu.dispose` in the same file. `input.attach`/`detach` is also distinct, but the verb fits (DOM coupling, not engine resource).

`frame.loop` returns a `FrameLoopHandle` with `stop` / `pause` / `resume` — a third verb family. Defensible (a loop isn't a resource), but worth noting that consumers learn three patterns: `create`/`destroy`, `attach`/`detach`, `stop`/`pause`/`resume`.

**Opinion:** leave as-is. Renaming `dispose → destroy` is a real breaking change for marginal gain. Document the three vocabularies in `engine-conventions.md` if not already.

### §9.2 Setup boilerplate is the biggest ergonomic tax today

**Observed pattern**, in every single cookbook demo (camera, blend, geometry, render-target, post, shader, animation):

```ts
let foo: T | undefined;
let bar: U | undefined;
let cube: Mesh | undefined;
try {
  foo = await x.create(...);
  bar = await y.create(...);
  cube = mesh.cube(ctx, { material: foo });
  return {
    scene: { foo, bar, cube, ... },
    dispose: () => {
      mesh.destroy(cube);      // reverse-creation
      y.destroy(bar);
      x.destroy(foo);
    },
  };
} catch (e) {
  if (cube) mesh.destroy(cube);   // reverse-creation, AGAIN
  if (bar) y.destroy(bar);
  if (foo) x.destroy(foo);
  throw e;
}
```

**Cost.** Two parallel cleanup arms (success path + catch path). Linear in resource count. Post and render-target each have 6–8 resources; the cleanup blocks dominate the setup file. **Every demo file in the cookbook duplicates this pattern.** It's the single most repeated piece of code in consumer-facing furnace usage.

**Why it exists.** TypeScript narrowing requires the `let foo: T | undefined; ... if (foo)` dance so the catch block can be type-correct without `!` or `as`. The duplication between dispose and catch is because the TS compiler can't share the cleanup logic across both arms without a helper.

**Proposed shape: a `DisposalBag` consumer helper.**

```ts
const bag = createBag(); // small core or cookbook helper
try {
  const mat  = bag.track(await material.unlit(ctx, { ... }), material.destroy);
  const cube = bag.track(mesh.cube(ctx, { material: mat }), mesh.destroy);
  return { scene: { mat, cube, ... }, dispose: () => bag.disposeAll() };
} catch (e) {
  bag.disposeAll();
  throw e;
}
```

Or, more aggressively, a TC39 `using`-style explicit-resource-management pattern when TS 5.2+ stabilises that path in the toolchain.

**Where to land.** Probably as a `@furnace/core` export (`core/dispose`?) since the pattern is universal. Could equivalently land in `mountDemo` as a passed-in bag — but that hides it from non-cookbook consumers.

**Cross-references.** Adjacent to §1.2 (engine-cascade-teardown — the engine's own internal-resource cascade). The two solve related problems (orderly teardown) at different layers; the consumer-facing bag would be a peer to `gpu.onDispose` plumbing.

### §9.3 Missing base concept — Scene / DrawList

**User-flagged**, and the investigation confirms the gap is real.

**Today.** `frame.render` takes `{ draw: Mesh[]; camera: Camera; effects?: Effect[]; clearColor?; clearDepth? }`. `frame.renderToTexture` takes the same bundle plus `texture: GPUTexture` and optional `depthTexture: GPUTexture`. The bundle is exported as `RenderOptions` / `RenderToTextureOptions` but has no semantic identity — it's "the args to render". Consumers manage:

- Membership: which meshes belong together (a `cube` + `backdrop` array tracked in the closure).
- Camera binding: which camera renders this list.
- Effects chain: which effects post-process this list.
- Per-frame draw-list construction: every frame, build the array.

**Render-target is the load-bearing example.** It builds *two* draw lists per frame:
```ts
frame.renderToTexture(ctx, { draw: [subjectMesh, roomMesh], camera: pipCam, ... });
frame.render(ctx,         { draw: [roomMesh, subjectMesh, monitorMesh, gizmoMesh], camera: mainCam, ... });
```

The roomMesh appears in both lists. The consumer manages this overlap by hand. There's no "scene" object to ask "which meshes are in you".

**Two grades of fix.**

**Grade A (cheap, today).** Surface `RenderList` (or `Scene`) as a structural type alias + ship a small builder:

```ts
type RenderList = {
  meshes: Mesh[];
  camera: Camera;
  effects?: Effect[];
  clearColor?: ClearColor;
  clearDepth?: number;
};

// Consumer:
const mainList: RenderList = { meshes: [roomMesh, subjectMesh, ...], camera: mainCam, clearColor: CLEAR_MAIN };
frame.render(ctx, mainList);
```

Functionally identical to today (since `RenderOptions` already IS this bundle); the lift is naming + ergonomics + treating draw-lists as values that can be passed around. Tiny core change, real consumer clarity win.

**Grade B (heavier, future).** Stateful `Scene` with `add` / `remove` / `setCamera` / `clearColor` properties / `effects` chain — the engine tracks membership, draw order, and config:

```ts
const scene = scene.create({ camera: mainCam, clearColor: CLEAR_MAIN });
scene.add(roomMesh);
scene.add(subjectMesh);
scene.setEffects([bloom, vignette]);
frame.render(ctx, scene);
```

Bigger design discussion (mutation timing, ownership, what about removed meshes' lifetime, does it pair with scene-graph parent/child from the existing `scene-graph-helpers.md` backlog?). Pushes toward Tier-2 framing.

**Opinion:** Grade A is a low-cost win that surfaces the concept and lets consumers pass draw-lists around as values. Grade B is the right end-state but needs its own brainstorm — strong overlap with `scene-graph-helpers.md` (Tier 2). Grade A doesn't preclude Grade B; it warms it up.

**Cross-references.** Adjacent to `scene-graph-helpers.md` (§4, Tier-2 deferred). Grade A is Tier 1 work; Grade B promotes the scene concept into the design discussion for that backlog item.

### §9.4 `frame.render` vs `frame.renderToTexture` — Pass abstraction

**Today.** Two near-identical functions:

- `frame.render(ctx, { draw, camera, effects?, clearColor?, clearDepth? })` — color target is the swap chain; supports an effects chain.
- `frame.renderToTexture(ctx, { texture, depthTexture?, draw, camera, clearColor?, clearDepth? })` — color target is a consumer-supplied `GPUTexture`; no effects chain (uses depth optionally).

**Overlap is ~80%** of the option shape. Consumer has to decide which function to call based on "do I want offscreen or onscreen". The choice maps cleanly to the `target` field of a single function:

```ts
type RenderTarget =
  | { kind: "swapchain"; effects?: Effect[] }
  | { kind: "texture"; texture: GPUTexture; depthTexture?: GPUTexture };

frame.render(ctx, { target, draw, camera, clearColor?, clearDepth? });
```

Or a less aggressive union — keep the two functions but extract a `Pass` type that documents the shared shape.

**Cost of unifying:** breaking change to `frame.renderToTexture` callers (render-target is the only one). Pedagogically clearer; reduces "which function?" decision point.

**Cost of keeping split:** documentation overhead (two near-identical reference tables), the "effects chain only works on the swap-chain path" footnote, occasional consumer confusion about which fields are valid where.

**Opinion:** worth a brainstorm. The unification is small, the consumer-clarity win is real, and it would pair cleanly with the Grade-A Scene/RenderList work in §9.3. But not load-bearing — leaving it split is fine and matches established WebGPU library conventions (Three.js has `renderer.render` + `renderer.setRenderTarget`).

**Cross-references.** Adjacent to `multi-camera-passes.md` (Tier-2 deferred — that entry proposes `frame.render({ passes: [...] })` for multi-pass scenes, which is a different shape but related concept space).

### §9.5 Color tuple type repeated inline everywhere

**~~LANDED in Tranche A (commits 8daf8f5–183d5bd).~~**

**Today.** `[number, number, number, number]` appears as the color shape in:
- `frame.ClearColor` — exported, but `frame`-scoped.
- `material.UnlitOptions.color` — `[number, number, number, number]` inline, NOT named.
- Every cookbook demo's `CLEAR_COLOR` constant — inline `[number, number, number, number]`.
- Many `material.unlit(ctx, { color: [...] })` call sites — inline tuple.

`frame.ClearColor` exists but isn't reused by `material.UnlitOptions.color` — they're the same shape with different names.

### §9.6 Camera doesn't auto-update on canvas resize — every demo computes aspect once

**~~LANDED in Tranche A (commits 50d2e60–cf92002).~~**

**Observed in every demo:**

```ts
const cam = camera.perspective({
  aspect: ctx.canvas.width / ctx.canvas.height,
  position: vec3.fromValues(0, 0, CAMERA_Z),
});
```

Aspect is read once at setup. **No cookbook demo subscribes to `gpu.onResize` and calls `camera.setAspect`.** Result: every demo's projection distorts when the user resizes the window. The engine ships `gpu.onResize` and `camera.setAspect` — the wire-up is just missing.

`engine-conventions.md` documents this explicitly: "Aspect ratio is consumer-managed: subscribe to `gpu.onResize` and call `camera.setAspect(cam, width / height)`." So this is "consumer responsibility per design" — but if every consumer skips it, the design is making the wrong thing the default.

**Three fixes, in order of intrusiveness:**

1. **Just fix the cookbook.** Every demo's `setup` adds the four-line subscribe-and-update wire-up. Doesn't move the engine API; teaches the pattern. Fixes the bug.
2. **Cookbook helper.** `mountDemo` grows a `camera?: Camera` field; if passed, auto-wires it to resize. Cookbook-only.
3. **Engine helper.** `camera.bindToCanvas(cam, ctx)` or `camera.autoAspect(cam, ctx)` returns an unsubscribe; subscribes internally to `gpu.onResize`. Engine surface grows but the common case becomes one line.

**Opinion:** start with (1) — fix the bug in every demo as a quick mechanical pass. If the fix is genuinely four lines × seven demos, that's tolerable. If it grows (multiple cameras, per-camera aspect handling), consider (3). Avoid (2) — `mountDemo` shouldn't accumulate framework-y features.

**Cross-references.** None. Net-new finding. Strong recommendation: bundle the cookbook fix into Tranche A (quick wins) — the bug is in the primary-browser experience today.
