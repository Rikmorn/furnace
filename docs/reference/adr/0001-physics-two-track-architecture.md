# ADR 0001 — Physics architecture: two-track (CPU-authoritative gameplay / GPU-resident visual), borrow the CPU solver

**Date:** 2026-06-01
**Status: Accepted.**
- The two-track posture, CPU-first for Demo 1, borrow-not-build, and the clean-wrapper abstraction.
- **CPU backend resolved → Rapier** (`@dimforge/rapier3d`), chosen as the *simple start*. Reversibility is secured by the wrapper's backend-neutral, thread-ready event API (Decision 7), not by the engine underneath — so Jolt is a documented scale-up swap (`docs/backlog/engine-architecture/jolt-backend-swap.md`), not a fork in the road. Resolved 2026-06-01 after a threading / scalability / debuggability evaluation (which superseded the earlier vehicle-physics framing).

**Evidence:** `docs/research/2026-06-01-gpu-resident-vs-cpu-gameplay-physics.md`, `docs/research/2026-06-01-gpu-resident-physics-solver.md`, `docs/research/2026-06-01-cpu-physics-backend-comparison.md`, `docs/research/2026-06-01-rapier-vs-jolt-threading-debuggability.md`.

## Context

furnace adopted demo-driven development; Demo 1's "one big thing" is physics. The initial plan was **GPU-resident** rigid-body physics (solver writes the buffers the renderer reads, no CPU↔GPU copy) — chosen to "solve it once on the GPU." Two research passes overturned that as the *gameplay* foundation:

1. **Solver research** — stable rigid-body stacking is XPBD's documented weak regime; GPU is *worst* at exactly what bowling needs, and *best* at particles/cloth (which bowling isn't).
2. **Strategic research (25/25 verified)** — the field is near-unanimous: gameplay-critical rigid-body physics is **CPU-authoritative** (Jolt, Box2D, Rapier, Havok, PhysX-CPU); GPU physics is reserved for visual/throughput sim. The reasons are structural: the WebGPU readback wall (`mapAsync` async + mutually-exclusive; gpuweb#1972 still open) stalls CPU game logic, and GPU floating-point is **not cross-GPU deterministic** (a near-blocker for lockstep/replay). Even PhysX 5 GPU keeps joints/CCD/triggers on the CPU; Niagara collision events don't fire on GPU sims.

## Decision

1. **Two-track posture.** CPU-authoritative physics for gameplay-critical/interactive simulation; GPU-resident physics as a *separate, deferred* track for visual/throughput sim (particles, cloth, fluids, large-scale debris). They are different tools for different jobs, not competitors.
2. **Demo 1 (bowling) = CPU-authoritative, built first.** It's interactive rigid-body physics — the CPU track's home.
3. **Borrow, don't build.** CPU rigid-body physics is a solved domain. Borrow a mature engine; do not write a second solver. (The GPU-resident track, when it comes, *is* build — no borrowable WebGPU-resident engine exists.)
4. **Clean wrapper.** The borrowed engine is sealed behind furnace's own `physics` API — consumer code never imports or sees the backend. This is a clean wrapper over *one* backend (good hygiene), **not** speculative pluggable multi-backend machinery.
5. **furnace-owned concepts.** `static` / `dynamic` / `kinematic` body types are the durable, backend-agnostic abstraction. **Transforms stay JS-authoritative** (the existing `mesh.setPosition` path) — the GPU-resident source-of-truth inversion does not apply; gameplay logic reads state for free.
6. **Backend (RESOLVED): Rapier** (`@dimforge/rapier3d`) — the simple start. Both were spiked headless under `bun:test`. Rapier wins on *integration* for a wrapped backend (smaller wasm — 571 vs 708 KB gz; Rust/wasm-bindgen with cascading `World.free()` vs C++/emscripten-embind manual per-object destroy; ready `-deterministic` npm package) and minimises wrapper cost for the immediate problem (bowling). The threading/scalability evaluation (`docs/research/2026-06-01-rapier-vs-jolt-threading-debuggability.md`) found a *real* Jolt advantage — it ships **multithreaded wasm** that scales one simulation across all cores, whereas the published Rapier is **single-threaded wasm** (binary-verified) and furnace's wasm architecture cannot reach Rapier's native parallel solver. But single-scene multicore is **deferred headroom** for furnace, and the backend-neutral wrapper (Decision 7) makes it cheaply reversible — so we start simple with Rapier rather than pay Jolt's heavier wrapper (manual emscripten memory, cross-origin-isolation setup, leaky threaded JS callbacks) for a need we are deferring. Jolt is the documented scale-up backend (`docs/backlog/engine-architecture/jolt-backend-swap.md`).
7. **The wrapper is backend-neutral and thread-ready by design — this is the real future-proofing, not the engine choice.** Collision/contact events are exposed as a **drainable queue read *after* each `step()`**, never as mid-step push-callbacks. This one shape is portable across both engines (it is already how Rapier's `EventQueue` works), thread-safe under Jolt's Emscripten-worker model (where mid-step C++→JS callbacks break at the worker boundary — workers share linear memory but not JS objects), and leaks no backend internals to consumers. It is what turns the backend from a one-way door into a reversible choice, and keeps the multicore-scaling path open regardless of which engine sits underneath.

## Consequences

- **GPU-resident compute-substrate work defers** to a future GPU-visual demo (it's not lost — that demo is a better vehicle for it, aimed at GPU's actual strength).
- **Gameplay logic is easy** — JS-authoritative state, no readback wall. This is the main practical win.
- **A wasm dependency** (~570–840 KB gz depending on engine/packaging) loads **only for physics consumers** — it lives behind `@furnace/core/physics` and is tree-shakeable; non-physics consumers pay zero.
- **Determinism / networking deferred** (`docs/backlog/engine-architecture/physics-tracks.md` §CPU-authoritative physics). Rapier ships a ready `-deterministic` package; Jolt requires a self-built CMake flavour — a factor in the backend choice.
- **Scope ~halves** vs the GPU epic (~12–15 vs ~26–28 phases) and the deleted half is the riskiest novel work (GPGPU substrate + from-scratch solver + graph coloring) — replaced by battle-tested code.
- **The wrapper gives bounded reversibility.** Because consumers never see the backend, switching Rapier↔Jolt later means rewriting the wrapper's internals — real work, but consumer code is untouched. This is "which to start with," not "marry forever." The reversal cost is *asymmetric* and must be designed for — which is exactly what Decision 7 (drainable event API, no mid-step push-callbacks) front-loads.
- **Single-scene multicore CPU scaling is deferred, but with a written strategy.** The published Rapier is single-threaded wasm (one core per `World`; more cores only via independent worlds on separate Web Workers — data-parallel across non-interacting scenes, never one coupled scene). furnace's wasm architecture cannot reach Rapier's native `rayon` parallel solver; single-scene multicore from Rapier would mean maintaining a custom `wasm-bindgen-rayon` build. Jolt ships single-scene multicore wasm off the shelf. The strategy: defer scaling, build the neutral/thread-ready wrapper now, and swap to Jolt (or offer a consumer-selectable backend) when a demo actually needs it.
- **Threading isolation is target-dependent.** Jolt's threaded build needs `SharedArrayBuffer` → cross-origin isolation (`COOP`/`COEP`). On the open web that is an external, document-scoped cost; **on native (the wry WebView furnace ships) furnace owns the origin and headers, so isolation is self-administered.** The deferred Jolt path is therefore more accessible on native than a browser-only framing implies.

## Alternatives considered

- **GPU-resident rigid body (original plan)** — rejected as the gameplay foundation (GPU weak at stacking; readback wall; cross-GPU non-determinism). Retained as the deferred *visual/throughput* track.
- **Build our own CPU solver** (TS or Rust→wasm) — rejected for *real* rigid-body needs (solved domain; huge effort to parity). A tiny TS kinematic solver remains the right call only for *arcade-simple* future needs.
- **Jolt instead of Rapier** — not rejected, *deferred*: the documented scale-up backend (`docs/backlog/engine-architecture/jolt-backend-swap.md`). MIT, broader AAA featureset, and the only off-the-shelf path to single-scene multicore CPU physics in furnace's wasm architecture. Chosen *against as the starting backend* on wrapper-cost / now-simplicity grounds (manual emscripten memory, cross-origin-isolation setup, leaky threaded JS callbacks) — all cost paid for headroom furnace is deferring. The neutral wrapper (Decision 7) keeps the swap cheap.

## Resolved (2026-06-01)

**Rapier vs Jolt → Rapier, start simple.** The reopening (initially framed around vehicle physics) was refocused onto performance, multi-threading/scalability, and debuggability (`docs/research/2026-06-01-rapier-vs-jolt-threading-debuggability.md`). The evaluation surfaced a genuine Jolt advantage (shipped multicore wasm; Rapier is single-threaded and furnace's wasm model cannot reach its native parallel solver) — but that capability is **deferred headroom**, and the **backend-neutral, thread-ready wrapper (Decision 7)** makes the choice reversible. So: solve the immediate problem with Rapier's lighter wrapper; keep the scaling door open by design; track Jolt as the scale-up swap (or a future consumer-selectable backend) in `docs/backlog/engine-architecture/jolt-backend-swap.md`. The four evidence gaps from the lighter research run are recorded there, to be filled when the Jolt trigger fires.
