- **Sealed:** 2026-06-29
- **Package(s):** dungeon (prose states "No `@furnace/core` change")
- **Gate:** multi-level + off-axis feel gated visually (Safari/Chrome)

**Epic 2 · Slice 2.2.4 ("Seams — the connection primitive") then landed (2026-06-29):** today's three special-cased connection mechanisms — cardinal-snap room↔cave join, the flat `vestibule` bridge, and the hand-tuned `AREA_ORIGIN` authored↔generated seam — were replaced by ONE general portal-join + walkable-connector primitive, proven on a hand-composed multi-level arrangement of the existing dungeon. A new `packages/dungeon/src/walkability.ts` single-sources the locomotion constants (`STEP_HEIGHT`/`STEP_MARGIN`/`SLOPE_LIMIT_RAD`/`SLOPE_LIMIT_COS`) that `char-move.ts`, `themes/box-room.ts`, and the new router all read — so connectors are walkable by construction (the `GROUND_SNAP >= STEP_HEIGHT` invariant, with `GROUND_SNAP` still owned by `char-move.ts`, is now unit-asserted; `box-room.ts`'s duplicate `STEP_HEIGHT` is retired, now re-exported from `walkability.ts`). `packages/dungeon/src/connect.ts` holds the pure join + connector-routing primitives: `join(a, b)` computes the continuous-yaw + height `Placement` seating portal B's opening onto portal A (B's outward facing → A's INWARD facing −A.facing — the general case of the retired cardinal-snap), and `placePiece(region, place)` applies it across a whole `RegionData` (mesh/collider positions rotated+translated, per-piece rotation composed with the yaw, connection facings rotated, instance transforms + placements transformed). `route(from, to, opts?)` returns a connector `RegionData` walkable by construction — `chooseKind` picks **corridor** (flat) / **ramp** (one pitched slab gated by the slope limit) / **stairs** (reusing `box-room.ts stepBoxes`, each riser < `STEP_HEIGHT − STEP_MARGIN`) from the height delta over the run, or `opts.kind` forces one (setup-loud throw when a forced ramp's pitch exceeds the slope limit); the connector floor overlaps both portals by ≥1 cell (`SEAM_OVERLAP`). The `region.ts` contract gains `RegionMesh.rotation?`/`RegionCollider.rotation?` (quaternion, absent = identity) + `Provenance.theme: RegionKind` (= `ThemeName | "connector"`); `realize.ts` applies mesh rotation via `mesh.setRotation` and collider rotation via `createBody({rotation})` (the body-rotation path scatter already used). The migration: `compose.ts placeRoom` is now `placePiece(room, join(target, door))` (cardinal `yawMap`/`rotateExtent`/`rotateShape` deleted); `buildArea` gaps each branch room `ROOM_GAP` beyond the cave mouth and bridges it with a `route` corridor (`vestibule` + `snapCardinal` deleted — the corridor IS the vestibule's flat case from the general primitive); a shared `attachWing(seed, chamberDoor, gap)` helper seats the generated wing onto the authored chamber's exported `CHAMBER_DOOR` Connection via `join` + a `route` corridor (deleting `main.ts`'s `AREA_ORIGIN` GATE-TUNE), called by BOTH `main.ts` and the `traversal.gpu.test.ts` harness so they can't drift. The proof: `attachUpperLevel` adds a hand-composed second storey on the existing dungeon — a `pillarHall` reached by a ~30° **off-axis** ramp (a non-cardinal join yaw, exercising the rotation pipeline end-to-end) and a `greatHall` reached by a **cardinal stair-run**. End state: **one join path in the codebase**. **No `@furnace/core` change** (`mesh.setRotation` + `BodyDescriptor.rotation` already existed). Headless: `tests/walkability.test.ts` (`GROUND_SNAP`/slope invariants), `tests/connect.test.ts` (`join`/`placePiece` general + cardinal-regression, `route` kind-selection + walkable-by-construction + forced-ramp throw + seam overlap), `tests/connect.gpu.test.ts` + `tests/realize-rotation.gpu.test.ts` + the `area-traversal.gpu.test.ts` ramp/stair climbs (the CharacterMover walks routed ramps + stairs + the off-axis upper room), and the re-anchored `traversal.gpu.test.ts` (cave-hub fuzz + level↔wing `attachWing` seam) are `.gpu.test.ts`-covered; placement/route math is unit-tested; the multi-level + off-axis feel stays a visual gate (Safari/Chrome). A descending-stair / forced-down-ramp robustness gap (a high→low `route` emits an empty/unwalkable stair connector, and a forced steep descending ramp builds instead of throwing) was noted for 2.2.5 (resolved in Slice 2.2.5a below — see the `route` hardening).
